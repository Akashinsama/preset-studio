# 预设生成器 · 工程设计草案

> 状态：设想阶段（v0）。等边界确认后开工。
> 来源：由本次「芳乃预设」的构建流水线泛化而来。形态 = 本地 Web GUI；范围 = 先做只读三阶段。

## 0. 一句话

一个本地零依赖的 Web 工具，把 **读预设 → 出计划 → 渲染预览 → 编辑框架** 四件事做成鼠标流。
**结构由工具管，正文由你写。**

## 1. 技术选型：为什么是"零依赖静态页"

| 决策 | 理由 |
|---|---|
| 纯静态单页，双击 `index.html` 即开 | 环境事实：DSH 沙箱里 HTTPS 不可用，`npm install` 不可靠；不引依赖是最稳的 |
| 不引任何 CDN | 反面教材：梦鲸面板从 `testingcf.jsdelivr.net` 拉 Vue/Pinia/Zod，断网即废。我们踩过这个 |
| 读文件用 `<input type=file>`，存草稿用 localStorage，导出用 Blob | 都不需要服务器与任何权限申请 |
| 复用现有测试基建 | headless Chrome 真浏览器 + 假 DOM shim 已经跑通 400+ 断言，直接用来测 GUI |

技术上它是**单个 HTML + 若干零依赖 JS 模块**，和现有 `panel/` 一个路子。

## 2. 四块功能

### A. 解析器（只读）

输入 N 份预设 JSON，输出结构化视图：

- **条目表**：名字 / 槽位 / role / 注入位置 / 顺序 / 长度 / 开关 / 内容指纹
- **槽位占用表**：谁占了 `main`/`jailbreak`/`worldInfoBefore`…，冲突高亮，落败者标记
- **变量总线**：谁 `setvar`、谁 `getvar`、谁 `addvar`；悬空引用；**跨文件撞名**（本次撞了 `qianghua`/`zhuanshu`）
- **依赖图**：条目 A 的 `{{getvar::x}}` → 依赖条目 B 的 `{{setvar::x}}`；箭头画出"谁给谁供数"
- **标签族识别**：`<think…>` / `konatan_planning~` / `<UpdateVariable>` / `<current_event>` / `<progress>`…
- **外部依赖**：非原生宏（如 `{{压缩相邻消息::}}`）、插件、CDN
- **正则清单 / 内嵌脚本清单**
- **自动分组建议**：带推断依据（见 §4）

### B. 计划器（只读）— MVP 核心

输入：来源 + 槽位归属策略 + 分组规格。输出 `plan.json` + 人可读报告：

- 搬运清单 / 槽位主人 / 降级为普通条目 / 丢弃
- 段落顺序（**块间可排，块内严格保序**——梦鲸靠 `addvar` 累加、Izumi 靠"初始化变量"在前）
- 默认开关矩阵
- **不变式检查结果**（见 §3）

计划可 **diff**：换一份来源或改一条策略，直接看差异——这是"可审查的中间产物"，比直接出成品安全得多。

### C. 渲染器（浏览器端）— 最有价值的一块

1. **拼装模拟器**
   按 `prompt_order` 顺序模拟 SillyTavern 的组装，**带状态地展开变量**（`setvar`/`getvar`/`addvar`/`trim` 按出现顺序执行，维护一张变量表），内置槽显示为占位块：

   ```
   ⟨角色卡描述⟩  ⟨世界书:前⟩  ⟨聊天记录⟩
   ```

   输出**"实际会发给模型的那段文本"**，逐段标注来源条目 + token 估算。

   > 这块是本次两起事故的直接解药：有它就能一眼看到"切到其他模型后 `<DATA>` 包裹与角色卡注入位全没了"、"ICOT 与 Izumi 思维链同时生效"、"MVU 生产者开着但没有消费者"。

2. **面板预览**
   把预设内嵌的面板脚本放到 **iframe + 假 TavernHelper** 里跑（假 API 已经在 `panel/preview-host.js` 里实现过）。
   **绝不 eval 第三方脚本到主页面。**

3. **对照视图**
   同一份预设，不同分支 / 不同模型设置下的拼装结果并排比。

### D. 框架编辑器（半写入）

- 增删条目、改分组与模式（单选/多选/必选一/可全关）、调顺序、声明槽位归属与依赖关系
- **新增条目的正文留白**：工具只生成**结构骨架**（标签、变量位置、插入约束）+ 一份填写说明；正文由使用者写
- 未填条目在视图里标 **待填**，且**禁止被设为默认开启**（沿用本次 `雪融雪降` 的教训）
- 编辑的是**规格**，不是成品预设

> 关键边界：**工具永远不写提示词正文。** 它只负责骨架、位置、依赖与校验。
> 这条同时解决了"不改来源正文"与"要能自定义"的矛盾——来源条目逐字节搬运，新增条目留白。

## 3. 不变式：把本次踩过的坑变成编译期断言

这是本项目最贵的资产，全部固化进生成器：

| 不变式 | 来自哪次事故 |
|---|---|
| **锚点不得进入任何可开关分组** | 切模型后丢世界书/角色卡/主提示 |
| 一个 `identifier` 只能有一个主人 | 槽位冲突 |
| 同时开启的思维链标签族必须唯一 | 两种思维链混排 |
| 来源条目哈希必须逐字节相等 | "人家的东西不要动" |
| **成套性**：功能条目必须连带它的搭档 | MVU 只开生产者、摘要只搬提示词漏掉 4 条正则 |
| 必填但未填的条目不得默认开启 | 带着别人的占位文本上线 |
| 成品只允许一份、文件名固定 | 导入时拿错旧版 |
| 面板必须能在 390×844、嵌套 iframe、transform 祖先下渲染 | 手机打不开 |

其中**"成套性"是个新概念**：用 `provides: [A]` / `requires: [B]` 声明，工具自动报"缺搭档"。本次两起事故本质是同一个病。

## 4. 自动推断：从条目正文推出语义（准确率可量化）

本次 `groups.json` 里大量东西是手工标注的，其实大多可推：

| 推断目标 | 判据 |
|---|---|
| 覆盖式开关（单选候选） | 正文有 `{{setvar::x::…}}`，且别处有 `{{getvar::x}}` 消费 |
| 累加式开关（可叠加） | 正文有 `{{addvar::x::…}}`（梦鲸那套） |
| 互斥族 / 必选一 | 同一变量被 N 条**同时** setvar → 天然互斥；若无法全关则"必选一" |
| 槽位占位 | `identifier` 命中内置槽清单 |
| 思维链标签族 | 正文/正则里出现 `<think…>` vs `konatan_planning~` |
| 需用户填内容 | 正文含"自定义/自填/此处添加/点进去看"等模式，或极短且含占位括号 |
| 破甲 vs 功能 | **推不出来**——这是人的判断，只给候选分组让人确认 |

★ **准确率可量化**：我们已经有 ground truth——本次手工标注的 `anchors`（12 条）、`thinkingTags`（2 组）、`DEFAULT_OFF`、`EDITABLE`（7 条）、各模块 `mode`。自动推断跑一遍与手工结果对比，就能算出准确率。这比"看起来像"可靠得多。

**必须显示推断依据**，否则作者不敢信；推断结果永远可被人工覆盖，且人工优先级最高。

## 6. 明确不做

- **不写提示词正文**（只搭骨架、留白、检查是否填了）
- **不评测破甲效果**（结构测到死，行为交使用者实测——本次 400+ 断言一条都没测效果）
- 不引任何依赖与 CDN
- 不在主页面 eval 第三方脚本

## 7. 风险

1. **每份预设都是手工艺品**：作者用 `</clear>`、假对话预填充、`addvar` 累加、按楼层奇偶的正则……自动推断必然误判 → 必须"推断 + 人工覆盖"双层，且推断可解释。
2. **"不改正文"与"变量撞名"的张力**：变量是全局的，消解冲突就得改正文 → 策略 `rewrite: none | prefix | explicit`，默认 `none`，每次改写都进报告。
3. **"破甲"没有客观边界**：哪些算破甲哪些算功能取决于模型与渠道，本质是人的判断 → 工具只提供分组与冲突检测，不替你决定。
4. **大预设性能**：3 MB JSON 在浏览器里解析与渲染要分页、惰性渲染，只建索引不复制。

### M6 实现时定下来的几件事

1. **分成两段配置块，而不是让生成器"生成代码"。** 面板里有两段被标记围起来的字面量：
   `CONFIG`（外观）与 `GROUPS_OVERRIDE`（分组，默认 `null`）。生成器只替换块内的字面量，
   于是"改配置"和"改代码"彻底分开——这也是唯一诚实的做法（任意 JS 不可能可视化编辑）。
2. **推断只用"可验证的事实"，不用语义猜测。** 全部依据：变量被多条非清空型条目设置（=作者写成互斥了）、
   变量被多条 addvar 累加、条目占着注入位槽位、条目是清空型初始化、思维链标签族、
   正文里写着"此处自定义"、名字前缀相同。名字前缀那条明确标着"是猜的"，界面上让人自己改。
3. **面板按条目名匹配，所以重名条目必须排除。** 不排除的话会出现"点开一个却关掉另一个"——
   这种 bug 在界面上看不出来，只会表现为"面板开关不灵"。推断结果里会写明排除理由。
4. **兜底模块保证"没有条目够不着"。** 推断完一定再收一个「其余条目」，哪怕它很大——
   面板上够不到某条，比模块划分得难看严重得多。
5. **每次断言都要能戳破自己。** 分组推断的测试包括：造小预设逐条验证规则、
   重名条目确实被排除、校验器能挑出四种真错（名字不存在 / id 重复 / mode 非法 / 分节引用不存在）、
   覆盖块写进去能被面板真的用上（`__FANO_PANEL__.groups` 等于覆盖值）。

### 做 M6 时踩到的三个坑

| 现象 | 真因 | 修法 |
|---|---|---|
| `extractGroups()` 把 `null` 读成了一个大对象 | `findLiteral` 只会找 `{`——而 `GROUPS_OVERRIDE` 默认值是 `null`，于是一路匹配到后面某个不相干的大括号 | 值和对象都支持：`{`/`[` 做配对，其它字面量读到行尾。**默认值是 null 的配置块，最容易在这里翻车** |
| 9 条条目在面板上够不到 | 兜底逻辑把 `thinkingTags` 的**全量**成员当成"已覆盖"，但模块只收了名字像思考链的那部分——剩下的既不在模块里、也不在兜底里 | "互斥执行"用全量成员，"已覆盖"只用**真的进了模块**的成员。两者是两个概念 |
| 自检跑完，界面还留着"已装面板"的样子 | 自检里 `attachPanel()` 会 `bump()` 重画；撤回时只清了状态、**没重画**，于是 dump 出来的是过期 DOM（浏览器检查因此读到错的按钮） | 撤回后补一次 `renderAll()`。凡是"改状态再 dump"的自检，都必须留下一次重画 |

另外两处更小的：`addScript` 的 id 撞车检查只看了源文件里的 id，连加两条会静默撞车（要把本次已新增的也算上）；
以及测试自己写错的两处（把 `null` 当成"对象结构"断言、把"顶层字段一个不动"当成"装了脚本还不变"——
装脚本必然多一个 `extensions`）。

### M5 实现时定下来的几件事

1. **改外观不走"生成代码"，走"配置块"。** 面板里放一段被标记围起来的 `CONFIG`（颜色覆盖 / 悬浮球 /
   窗口尺寸 / 圆角 / 缩放 / 不透明度 / 磨砂 / 壁纸），生成器只替换这一段，别的一个字符不动。
   这是"能可视化调外观"和"能可视化改任意 JS"的分界线——后者是骗人的。
2. **预览用面板自己的 CSS**（从源码里抽 `const raw = …` 那一整段），只额外加一小段把 `position:fixed`
   改成摆位的作用域覆盖。预览里看到的颜色/字号/圆角/壁纸，就是装上去之后的；另画一个像的没意义。
3. **窗口分四层**：底色层（背景色 + 不透明度 + `backdrop-filter` 磨砂）→ 壁纸层 → 压暗层 → 内容。
   分成四层是为了让"半透明 + 壁纸 + 文字仍可读"三件事互不打架；压暗层是给花壁纸兜底的。
   顺序就是层级，所以测试直接断言子节点的先后顺序。
4. **两处夹取逻辑必须一致，所以用测试锁死。** 面板里有一份 `CFG`（它自己算的生效值），
   `lib/panelconfig.js` 里有一份 `clampConfig()`（界面和预览用）。测试会把配置写进面板源码、真加载面板，
   再拿面板的 `__FANO_PANEL__.config().effective` 跟 lib 的夹取结果**逐字段 JSON 比对**——有一处漂移就报错。
   这是"两份实现"唯一站得住的做法。
5. **壁纸只作用在面板上**，不动酒馆整页：整页换背景属于酒馆主题/插件的活，抢 CSS 的风险大得多。
   本机图片会被内嵌成 `data:`，所以校验会算清楚"预设将变大多少"并提前警告。
6. **脚本编辑只给"代码框 + 语法校验 + diff"。** 语法校验用 `new Function` **只编译不执行**
   （测试里专门验证了副作用不会发生）；diff 是**按行多重集合**算的粗略 diff，只用来回答"改了多少行"。


### M2 的判据来自哪里

不变式不是凭空定的，全部对应本次工程真实踩过的坑（见 §3），但判据本身是通用的。
两条设计原则：

1. **拿不准的不写"必改"**。比如"没有 jailbreak 槽位"在某些预设里是有意为之（用深度注入代替），
   所以只做「提示」；而"世界书注入位不在生效条目里"必然导致内容消失，才是「必改」。
2. **判断要看展开之后的结果，不是原文**。源预设里大量"给人看的"条目包在 `{{//……}}` 注释里，
   展开后是空的——拿原文判断会误报"你把占位话术喂给模型了"。

### M3 实现时定下来的几件事

1. **预览的就是导出的。** 编辑态不是"在每个视图里各改一遍"，而是套到原 JSON 上现算一份新 JSON、
   重新解析一遍，再喂给 M0/M1/M2 和导出。共用一条路径，所以"预览和结果不一致"这类 bug 从结构上不存在。
2. **没动过的条目在导出时复用原对象**（`out.push(p)`，不是深拷贝再写回）。
   于是"来源一字未改"变成可验证的事实：`applyEdit` 空编辑时输出与原文件 **sha1 完全相同**（测试断言）。
3. **`enabled` 有两处**（条目自己的 + `prompt_order` 里的），酒馆读列表里那份。
   用户显式改过的，两处一起写；**没改过的一律保持原样**——原文件里有 3 条本来就不一致，
   不去"顺手归一化"（那等于偷偷改了别人的文件语义）。
4. **新增条目的正文是 `{{//待填：…}}`**，不是空字符串：在酒馆的小铅笔里看得见，
   展开后是空的（不进模型），而且体检器按"展开后"判断，所以不会把它误报成"你把占位话术发给模型了"。
5. **待填且开启 = 拦住导出**。工具不代写正文，那就不允许把空条目打开——这是"不代写"这条规矩的执行点。

### M4 实现时定下来的几件事

1. **骨架的形状是量出来的，不是拍出来的。** 先用 `tools/diag-order.mjs` 量了 Izumi 与成品的
   `prompt_order`，得到注入位的真实排法（`main → 世界书前/人设/角色卡描述/性格/场景/世界书后
   → 内容条目 → 示例对话/聊天记录 → 历史后置指令`），骨架照这个生成；顺序错了会导致
   "注入位缺失"甚至上下文丢失，那是我们这次工程最贵的一个坑。
2. **位置标记的正文真的是 0 字**，不是待填注释。一是真实预设就长这样（量出来的：这些条目
   正文全是 0 字），二是 M1 才能把它显示成"⟨世界书·前⟩ 酒馆在这儿注入"；
   如果塞一句注释，展开后什么都不剩，读者会以为这条坏了。
3. **main 生成时就开着且待填**，于是"没写核心指令"会被导出前检查拦住并点名。
   这是唯一一个"开着但必须逼你写"的条目——因为空着 main 的预设等于没有系统指令。
4. **正文所有权**：导入的预设里，来源正文**只读**；只有"你自己写的条目"（M4 生成的骨架、
   M3 新增的条目）才有输入框。这条规矩同时决定了两件事：`applyEdit` 只允许改写 `edit.own`
   里的正文，`verifySourceIntact` 也把它们从"来源"里排除。
5. **基底只抄顶层设置**（采样参数、上下文上限…），**不抄**条目、`extensions`（正则/脚本/面板）。
   正则和面板通常绑死原预设的条目名，搬过去只会变成一堆指向不存在条目的死规则。
6. **"能用但空"是可接受的交付**：生成完体检一次，注入位齐全、没有变量问题，唯一的必改是
   "主提示还没写"。这条必改就是这份工具的态度——结构我给，话得你说。

### 导出前检查为什么要单独盯"面板脚本"（真踩过）

现象：搭完面板点导出，拿到的文件**看着完全正常**（条目、顺序、其它扩展都在），
但里面没有面板脚本——装进酒馆什么都不会发生，而且屏幕上没有任何提示。
对账过三份桌面文件：原版 164.8 KB / 73 条 / 0 脚本；`-改.json` 265.5 KB / 73 条 / 1 脚本（78.8 KB，带配置块）；
`-改 (1).json` 165.8 KB / **76 条** / **0 脚本**。第三份多出来的正是画布上新建的条目（`新功能 1`、`新选项 1/2`），
也就是说：**在画布上搭了面板、然后直接点了导出**，而「装进这份预设」那一步从来没点过。

真因不是 bug，是**两条路没有在同一个地方被问清楚**：
面板是 `extensions.tavern_helper.scripts` 里的**一条脚本**，条目是 `prompts` ——
搭面板改的是脚本，导出导出的是整份文件；界面上"搭过了"和"装进去了"是两种状态，却长得几乎一样。

修法（三条一起上，缺一条就还会漏）：

| 做法 | 为什么这么定 |
|---|---|
| `exportChecks` 增加面板分支：搭过面板（画布有功能区／动过外观）但文件里没有面板脚本 → **必改** | 失败的方向要选安全的那一边：静默丢掉面板**不可恢复**（人不会去数脚本），被拦住随时能一键解开 |
| 结论摆在「导出新预设」第一张卡，附**一键补救**（`装进这份预设`）与一条明确活路（`这份预设就是不要面板`） | 拦住却不给路 = 把人堵死。活路按 `state.rev` 记账：只要再动一下画布，它就会重新问你 |
| 脚本在但 `enabled: false` → **提醒**；脚本在但界面改动还没写进去 → **必改** | "看着像装好了"的另一种形态。关着的脚本酒馆助手不执行，悬浮球不会出现 |

关键的反面约束：**没有搭建意图时一个字都不说**。"导入别人的预设、只改条目"是最常见的用法，
那份预设本来就没有面板，绝不能因此拦人——界面上读的是 `state.appearance` 这个**已有状态**，
而不是 `ensureAppearance()`（后者会顺手把状态建出来，于是"只是渲染了导航徽标"就会被当成"动过外观"，
每导入一份无面板预设都会被拦）。

顺带补掉一个**早就存在、被这次改动放大**的洞：`state.groupsDraft` 原本不认预设——
在 A 上搭的草稿切到 B 之后还留着，画布会拿 A 的条目名去画 B（那些名字 B 里根本没有），
现在还会照着 A 的搭建意图去拦 B 的导出。所以 `resetEdits()` 里给草稿记了 `groupsDraftKey`：
**换预设就丢掉草稿**（编辑态仍然每个预设各存一份，两件事不冲突——草稿是"正在搭的一半"，
留着半成品去改另一份预设没有任何意义）。`panelIntent()` 再挡一道，只认自己那份的草稿。

### 面板标题：留空不是"没有标题"，而是"面板自称芳乃"

同一个真实场景里紧跟着暴露的第二个坑：搭完面板装进**别人的**预设，导出、装进酒馆，
面板顶上写着 **`🌸 芳乃 · 预设面板`**。真因是两处默认值各自为政：

| 谁 | 标题留空时显示什么 |
|---|---|
| 画布 / 预览（`ui.js` 的 `panelTitle()`） | 这份**预设的名字** ← 看起来完全正确 |
| 真面板（`panel-core.js`：`CONFIG?.title \|\| '🌸 芳乃 · 预设面板'`） | 面板**源码里写死的那句芳乃** |

于是"预览的就是导出的"在这一个字段上不成立，而且是**最显眼的一个字段**：面板的署名。
修法是把标题在**写进预设的那一刻**落成具体的字，而不是留空让两边各自兜底：

1. `panelSourceWithEdits()` 一律带上 `title: panelTitle()`——装进预设、应用改动、
   导出 `.js`、导出预览页四条路共用它，所以四条路的标题必然一致；
2. `applyPanelEdits()` 把落好的标题**写回界面状态**（`A.config.title`）——否则输入框一直空白、
   而面板早就有名字了，人还是看不见自己面板叫什么；
3. 留空分两种情况，`extractFallbackTitle()` 从源码里把兜底文案读出来：
   **预设自带**的面板留空 → 用源码那句（那是作者的意图，画布跟着它才与真面板一致）；
   **生成器新装进**别人预设的面板留空 → 用那份预设的名字（装到谁家就写谁的名字）。
   判据是 `scriptViews().isNew`：这次才加进去的脚本，不认内置面板那句自我署名；
4. "还没应用"的判据从"整份源码是否相同"改成 **`A.dirty` 或"草稿贴回去会不会变样"**。
   这一条是被第 1 条逼出来的：标题的规范化会让源码与界面状态**永远差一点**，
   拿整份比对的话人永远解不开那道拦截——拦截必须只认"你真的改过什么"。

五个断言盯着它：写进去的 `title` 不是空串、等于预设名、外观页读回来的一致、
自己填了标题之后脚本与画布同时改口、新装进去的面板不认源码那句兜底；
Node 侧还有两条锁住"兜底文案还在、而且读得出来"，免得以后有人改了兜底却不知道两边怎么分工。

### 面板随身带的"芳乃"：装进别人的预设前，字与数据都要换掉

**怎么发现的**（用户提问引出）："别人用这个编辑器做出来的预设，里面会出现芳乃吗？"
实测答案是**会**，而且只要装了面板就一定会。四条路径全跑过（拿一份不含芳乃的第三方预设当靶子）：

| 路径 | 产物里「芳乃」 | 带进去的芳乃条目名 |
|---|---|---|
| 只装面板（无分组草稿） | 39 处 | **200 / 200** |
| 装面板 + 用推断出来的分组 | 39 处 | 200 / 200 |
| **从零搭一份**骨架 + 装面板 | 39 处 | 200 / 200 |
| 完全不碰面板（只改条目 / 正则） | **0 处** | 0 |

**真因**：`panel/fano-panel.js` 是**芳乃那份预设**的面板——文件头注释、日志前缀 `[芳乃面板]`、
兜底标题、悬浮球字形里写着芳乃，自带的模块表更是**芳乃那 233 条的条目清单**。
生成器把这份面板装进别人预设时，是整份复制过去的。

最重的一处不是那几个字，而是**那张模块表**：它不只是品牌问题——面板**默认要用它**，
装到别人家会列出一堆那份预设里根本没有的条目、开关点不动。M6 的 `groupinfer` 就是为这件事写的，
但默认路径一直没接上（"装进这份预设"只在用户先点过"自动推断"时才用目标预设的分组）。

**修法**：与标题同一条思路——**在写进预设的那一刻落成中性的字**，面板源码本体一字不动
（那是芳乃自己那份，就该写着芳乃；`check-preset.mjs` 还断言着"脚本是芳乃面板"）。
新增 `PresetPanelConfig.foreignPanelSource(src, opts)` 一处收口：按钮名落成这家的、自带模块表换成
这家的、按 `BRAND_PATTERNS` 去品牌化，最后**断言产物里没有「芳乃」**。
`ui.js` 的 `panelSourceWithEdits()` 只在 `A.source !== 'preset'`（= 这份预设里本来没有我们的面板）
时走它——注意这个判据是"**首次装进去 vs 更新已有的**"，跟"这份预设是不是芳乃的"没关系。

**两个概念要分清**（用户划的边界）：`FANO_PANEL_*` / `fano-antitrunc-v1` 这类**英文标识保留**——
它们回答的是"这是哪一支面板"；换掉的是**中文的芳乃字样**与**芳乃预设自己的数据**。
防截断模块里那句出处属于**署名**（原作 Kemini Dramatron v3.1），所以只去掉"芳乃预设 v2.8.1"
这个名字，署名本身留着——那是别人的劳动，不该因为我们改个名就连带抹掉。

**这次踩的三个坑，形状都会重复**：

| 现象 | 真因 | 修法 |
|---|---|---|
| 真浏览器里"一键补救"装不上面板，`panelScriptViews` 拿到空数组 | 绊线只守住了 lib **自己的输出**：草稿是在 `foreignPanelSource` 的断言**之后**才写进 `GROUPS_OVERRIDE` 的 | 断言必须覆盖**最终产物**：把写覆盖块挪进 `foreignPanelSource` 内部、放在断言之前（`opts.alsoOverride`），`ui.js` 不再自己写第二遍 |
| 分组数据里也有芳乃（`🌸芳乃 · 称呼`、`芳乃主体层（本预设新增）`） | 草稿是从"面板自带的那个分组"复制来的，于是数据带着芳乃字样一起走 | 新增 `neutralizeData()`：对**草稿**逐层替换。**推断出来的分组一个字都别动**——那是目标预设自己的条目名，改了面板就找不到它 |
| 装进去之后导出**永远**被拦（"分组还没应用"） | `panelIntent()` 拿**原样草稿**比脚本里那份（已被去品牌化），永远判成"没应用" | 比两种写法（原样 + 去品牌化），任一相等就算已应用。**与标题那条是同一个坑**：凡是"写的时候替你规范化"的东西，判断"应用了没"就得用同一套口径 |

**探针要覆盖"用户可能的起点"，不是"我想得到的起点"**：第一版探针只跑了"按目标预设推断分组"，
漏了"草稿是面板自带那份复制来的"——那恰好是浏览器自检走的路径，所以只有真浏览器才抓到它。
现在探针跑五条路径，并带一条**反向测试**：往面板源码里塞一句新的芳乃字样，
`foreignPanelSource` 必须抛错（绊线要能戳破自己）。
还有一处探针自己的毛病值得记：面板脚本在 JSON 里是**转义**过的字符串，
拿 JSON 文本去按 JS 语法读（`extractDefaults`、字形字面量）会读到**假 0**——一律扫解出来的脚本正文。

**验证**：五条路径产物里「芳乃」均为 0；`node tools/check-gui-browser.mjs` 桌面与手机各 235 项、
八个 Node 套件 874 项全绿。**没有为这次改动改过任何既有断言**——修法收敛在"写入那一刻"，
面板源码、芳乃成品、既有测试一个字节都没动。

**同一批里被撤掉的一条（记下来，免得以后有人又想加）**：原计划做"装进别人预设时，把**没动过的**
分组草稿改用推断结果"。查下来这条**不必做、而且有害**，已撤：

- **画布本来就会自己判**。`canvasState()` 先量"面板自带的分组跟这份预设对得上多少"，对不上
  （`ratio < 0.5`）就直接摆一版按这份预设推断的草稿当起点。实测：九域 `0.000`、Kemini `0.093`
  → 走推断；Izumi `0.869`、芳乃成品 `1.000` → 照自带那份画（那时成员名**本来就在它预设里**）。
  所以"别人的预设里看到芳乃那套条目名"这件事，画布早就不这么干了——想修的那个场景根本不存在。
- 它**真会改变行为**的地方（`ratio ≥ 0.5`）是把一份**对得上的**现成分组换成猜的，
  顺便让"画布上看到的"与"写进文件的"不是同一份（"预览的就是导出的"当场破功）。
- 最硬的一条：**"没动过" ≠ "不是我选的"**。界面上「清空成空面板」「加入所有条目」「按这份预设自动推断」
  摆出来的草稿同样是"程序摆的、你没动过"，但那是**用户点出来的意图**——忽略它会出现
  "点了清空成空面板，却装进去一版推断分组"。
- `draftTouched()` 的正当用途只有一个：**别拿"你只是看了一眼"去拦你导出**（`panelIntent` 里算
  `groups` 的计数）。这条线不能挪到安装路径上。

**已知残留**（留着待定，不在"芳乃字样"的判据里）：悬浮球上那个字形仍是 `芳`
（`CONFIG.ball.glyph`，是芳乃的简称）。它是**可配置项**、画布上看得见，
所以要在"装进别人预设"时改它，就得同时让画布与写入用同一套推导——属于另一件事。

### 输入框的颜色（以及画布根本没有颜色变量这件事）

使用者反馈"输入框的颜色改不了"。查下来是两层问题，第一层比第二层严重得多：

1. **画布上的面板元素压根没拿到任何 `--fp-*` 变量。** `previewStyle()` 只把变量发给了
   `.fp-preview .fp-root`（面板外观的预览栏），而「面板搭建」的画布是 `.canvaswrap .fp-root`
   （gui.css 把悬浮窗摆回文档流）。于是画布上的面板是一堆**没有主题变量的裸元素**——
   颜色在那上面怎么调都不动，"改了没反应"就是这么来的。
   预览栏一直是对的（有 computed-style 断言守着），所以**只查预览栏的测试永远发现不了**。
   修法：同一个变量块发**两个作用域**，并补一条**查画布 computed style** 的断言——
   这条断言第一次跑就红了，说明它抓的是真东西。
2. 输入框本身没有自己的颜色项：可编辑正文用 `--fp-bg-inset`、选项框用 `--fp-bg-raised`、
   边用 `--fp-border-strong`——一个"输入框"横跨三个语义不同的 token，标签上也看不出来。
   新增 `--fp-input-bg` / `--fp-input-border`（面板 THEMES 昼夜各一份 + `TOKEN_SPEC` 两行说明），
   `.fp-textarea` 与 `.fp-select` 统一改用它俩：改一下"输入框底色"，**面板里所有输入框一起变**。
   画布与预览里的示例输入框也从工具自己的 `.bigtext` 换成面板的 `.fp-textarea`，
   免得"画布上是灰框子、装进酒馆是另一个颜色"。

### 体检器自己的准确性也进测试

**拿成品预设当反例**：`preset/芳乃预设.json` 已经过了 108 项构建校验，
所以体检器在它身上报出任何「必改」都先当成体检器误报（测试里直接断言 `counts.err === 0`）。
这一条在开发中真的抓到了两类误报：

| 误报 | 真因 | 修法 |
|---|---|---|
| 26 组"选一"被同时打开 | "初始化变量（别动）"（92 个 setvar 里 91 个是空白）和 Kemini 的 `🔗`（20 个变量被置成**一个空格**）被当成了"选项" | 新增"清空型"识别：setvar 数量 ≥3 且 ≥80% 是空白值 → 不算选项（`e.clearer`）。用比例而不是"全空白"，因为初始化条目里常夹一两个默认值 |
| "你把占位话术喂给模型了" | `📋说明（点小铅笔看）`整条包在 `{{//…}}` 注释里，展开后是空的 | 待填/重复注入两项改用**展开后**的正文判定 |

### 实现时定下来的两件事

1. **解析模型里保留 `content` 原文。** 一开始为了省内存只留了 `head`（预览行），结果 M1 拿不到正文，
   `{{setvar}}` 全被展开成空字符串——测试立刻抓到（"拼装后使用者拿到最后写入的值"失败）。
   结论：M1 的价值全在正文上，1 MB 级别的预设留着原文完全无压力。
2. **"变量最终为空"汇总成一条，明细放结构化字段。** 真实预设（Izumi）触发 44 次，逐条列会把警告区刷爆，
   而它们的成因是同一个（"初始化变量"把所有开关置空、对应开关条目没开）。
   现在警告给一句人话 + 写入方，`result.emptyVars` 给明细供界面列。

### 实测数据（Izumi_0914.json，作为规模基线）

| 指标 | 值 |
|---|---|
| 条目 | 226（在提示词列表里 192，初始开启 60） |
| 开启条目原文合计 | 10854 字 |
| 拼装后正文 | **5267 字**（去掉注入位占位块后 ≈3.5k token） |
| 展开后为空的"开关型"条目 | 31 条（正文几乎全是 `setvar`） |
| 变量事件 | 90+ 条 set/get/add |
| 拼装耗时 | 1–2 ms |

**要记住的结论**：别拿"开启条目的原文合计"当上下文占用，开关型条目只设变量、不产出文本。
这个差值（10854 → 5267）正是 M1 存在的意义。token 估算还会再扣掉注入位占位块，
因为那些 `⟨世界书·前⟩` 是画给人看的，酒馆真正注入的是世界书/角色卡本身。

### 做 M4 时又纠正的三处判据（都是"骨架一生成就露馅"的类型）

| 现象 | 真因 | 修法 |
|---|---|---|
| 骨架刚生成，体检说"必改 0"，导出却被拦住 | `main-empty` 看的是**原文长度**：`{{//待填：…}}` 有 43 字，于是"写了" | 改成看**展开后**的正文长度，和导出前检查同一套判据 |
| 骨架里 jailbreak 是关的，体检却提示"没有这个可选注入位" | 判据用的是"生效条目"（listed && enabled），把"有条目、只是关着"也算成"没有" | 可选注入位改成看"**在不在列表里**"；完全没有才提示 |
| 骨架明明什么都没写，却显示占用 132 token | 注入位占位块（`⟨世界书·前⟩` 之类）被算进了正文 | token 估算扣掉注入位占位块，并单独给出 `bodyChars`；0 也说 0 |

三处都是同一个毛病：**拿"原文/中间产物"当"会进模型的东西"**。这跟 §8 里
"判断要看展开之后的结果"是同一条教训，值得单独记一笔。
